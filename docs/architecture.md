# Architecture

> Статус v0.2 · стек: Next.js 16 (App Router, Turbopack), React 19, TypeScript strict, Tailwind v4, three.js (кінематографічна сцена головної), Vitest, Zod. Бренд і UX-принципи — [brand.md](brand.md).
> Next.js 16 має зміни відносно попередніх версій (напр. `proxy.ts` замість `middleware.ts`, `PageProps`/`RouteContext` типи). Перед змінами читайте `node_modules/next/dist/docs/` (див. `AGENTS.md`).

## 1. Шари

```
 UI (src/app, src/components)           ← Ukrainian copy, SVG-візуалізації, форма, звіт
    │  (імпортує лише публічний API ядра)
 Core (src/core)                        ← інженерія + економіка, без залежності від країни/UI/IO
    │  CountryAdapter (інтерфейс)
 Countries (src/countries)              ← UA (операційна), DE/PL (бенчмарк-адаптери)
 Server (src/server)                    ← ліди, валідація, auth для CRM
```

Правило залежностей (перевіряється ревью і тестом «adapter independence»): `core` **не імпортує** `countries`, `app`, `server`. `countries` імпортує тільки типи й `prov()` з `core`.

## 2. Домени даних

Запитані домени й де вони живуть сьогодні (MVP) та куди ростуть:

| Домен | MVP | Фаза 2+ |

| sites | `ProjectInput.site` + `regionId` | геометрія (PostGIS), GIS-аналіз оптимальної точки |
| feedstocks | `FeedstockLineInput` + каталог `FEEDSTOCKS`/`ANIMALS` | лабораторні аналізи, історія партій |
| energyConsumption | `EnergyInput` | профілі навантаження (15 хв), рахунки OCR |
| projects | `Lead.input` + `verdict` | проєкти, версії моделі, документи |
| scenarios | `Assessment.scenarios/routeMatrix/sensitivity` | збережені користувацькі сценарії, порівняння |
| plants | — | реальні станції (клієнти після впровадження) |
| financialModels | `ScenarioResult.fin` | повна фінмодель (податки, робочий капітал, структура боргу) |
| regulations | `CountryAdapter.regulatory()` | база нормативних вимог із версіями й джерелами |
| equipment | параметри CAPEX у `engineeringParams.ts` | каталог постачальників, комерційні пропозиції |

| reports | сторінка `/report/[id]` з друком у PDF | серверний PDF, версіонування |
| experts | поле в CRM (нотатки) | мережа експертів, призначення, календар |

## 3. Ядро (`src/core`)

| Модуль | Відповідальність |
|---|---|
| `types.ts` | усі доменні типи (вхід, результати, вердикт) |
| `params.ts`, `engineeringParams.ts`, `scenarios.ts` | **реєстр параметрів із provenance** (значення, одиниця, тип FACT/ASSUMPTION/CALCULATION/ESTIMATE, джерело, країна, дата, довіра); `Params.get()` фіксує, що використано |
| `feedstockData.ts`, `feedstock.ts` | каталог, голови→тонни, DM→VS→CH₄, інгібування, сезонність |
| `climate.ts`, `climateBenchmarks.ts` | HDD, температура субстрату, профіль попиту на тепло, кліматичні аналоги |
| `digester.ts` | об'єм (HRT/OLR), теплобаланс, сховище, вибір технології з обґрунтуванням |
| `demand.ts` | що клієнт реально споживає (електрика, тепло), ціни |
| `energy.ts` | місячний баланс КГУ / котел / біометан, корисне тепло |
| `capex.ts`, `economics.ts`, `finance.ts` | компонентний CAPEX, OPEX, доходи, NPV/IRR/DSCR/окупність |
| `digestate.ts`, `logistics.ts`, `methane.ts`, `safety.ts` | дигестат, логістика, втрати метану, реєстр ризиків |
| `scoring.ts`, `quality.ts`, `verdict.ts` | 7 окремих балів, довіра/пропущені дані, вердикт за правилами |
| `assess.ts` | оркестрація: 3 схеми × 3 сценарії, вибір схеми, стрес-тести, беззбитковість |

`assess(input, countryAdapter) → Assessment` — чиста детермінована функція (тести: відсутність NaN, збереження енергії, порядок сценаріїв, незалежність від країни).

## 4. CountryAdapter

```ts
interface CountryAdapter {
  code; nameEn; currency; maturity: 'operational' | 'profile';
  params: Provenance[];                 // ціни енергії й газу, зарплати, ставки, коефіцієнт CAPEX, добрива, EF мережі…
  regions: Region[];                    // 12 середньомісячних температур, назви кількома мовами
  support: { summary; availableForNewSmallProjects; checkedOn; schemes: SupportScheme[] };
  regime: 'EU' | 'UK' | 'US' | 'CA' | 'UA' | 'GENERIC';  // набір дозвільних кроків
  biomethaneInjection: boolean;
  regulatory(ctx): RegulatoryItem[];
  approachNotes: { en: string[]; uk: string[] };
  priceTier: 'A' | 'B' | 'C';           // ціна звіту за країною проєкту
}
```

33 країни: Україна — відкалібрований адаптер (`ua.ts`); 32 національні профілі (`profiles.ts` → `buildAdapter`) — оцінки порядку величини з позначкою ESTIMATE/LOW. Схеми підтримки (тарифи, премії за біометан, гранти) моделюються **окремими сценаріями** з перевіркою умов (макс./мін. потужність, частка гною, статус), ніколи не у вердикті. Тест вимагає однакового набору `econ.*` параметрів у кожній країні.
Що країна **вирішує**: клімат, ціни, зарплати, ставку дисконтування, регулювання, підтримку. Що **не** вирішує: кінетику процесу, тепловий баланс, логіку розрахунку.

## 5. Якість даних

Кожен `Provenance` має `kind`, `source`, `country`, `date`, `confidence`. Сторінка `/methodology` і `docs/assumptions-registry.md` генеруються з того ж коду, що й розрахунок — розбіжності неможливі. Результат містить `assumptionsUsed` (перелік id) та окремо показує, що введено клієнтом vs припущено (`missingData`, `confidence.reasons`).

## 6. Вебзастосунок

Усі публічні сторінки — під префіксом мови `/[lang]` (25 мов, статична генерація; визначення мови й країни — [i18n.md](i18n.md)).

| Маршрут | Призначення |
|---|---|
| `/[lang]` | головна: скрол-історія процесу (three.js), аудиторії, «чи підходить вам», що ви отримаєте, FAQ |
| `/[lang]/calculator` | країна + регіон проєкту (автовизначення), 4 кроки, приклади-архетипи з 7 країн, безкоштовний скринінг на клієнті; повний звіт — за оплату |
| `/[lang]/pricing` | free / Full Report / Expert Review, ціна за tier країни проєкту — [pricing.md](pricing.md) |
| `/[lang]/samples`, `/[lang]/samples/[id]` | повні звіти-приклади (14 архетипів) — клієнт бачить, що купує |
| `/[lang]/report/[token]` | оплачений звіт за неповторним токеном; серверний перерахунок; `noindex` |
| `/[lang]/methodology` | умови 33 країн + реєстр припущень з джерелами |
| `/[lang]/biogas`, `/[lang]/biogas/[slug]` | SEO-хаб і 7 сегментних сторінок (en/uk) |
| `/[lang]/terms`, `/[lang]/payment/demo` | умови (шаблон), демо-оплата — [payments.md](payments.md) |
| `/admin` | CRM: замовлення й заявки (Basic Auth через `proxy.ts`, 503 у production без `ADMIN_USER/ADMIN_PASSWORD`) |
| `POST /api/checkout` | Zod-валідація, ціна лише з конфігурації, Stripe Checkout Session |
| `POST /api/payments/webhook/stripe` | перевірка підпису, звірка суми, «липкий» `paid` |
| `POST /api/leads` | валідація (Zod), honeypot, ліміт частоти, **серверний перерахунок вердикту** (клієнт не може підробити) |
| `PATCH /api/admin/leads/[id]`, `/api/admin/orders/[id]` | статус і нотатки |

Головна: повноекранна сцена three.js (`src/components/three/ProcessScene.ts`, code-split, адаптивна якість, reduced-motion, пауза поза екраном), керована розділами скрол-історії (`HomeStory`). Візуалізація результатів: SVG без бібліотек — анімована схема потоків (товщина ∝ енергії; `prefers-reduced-motion`), накопичений грошовий потік, торнадо чутливості, шкали балів. Дизайн: темний «hero» + світлі робочі поверхні, табличні цифри, висока контрастність, адаптивність від 360 px.

## 7. Дані та CRM

`LeadRepository` (інтерфейс) → `fileRepository` (JSON-файл `data/leads.json`, атомарний запис, послідовна черга). **Це MVP-рішення**: працює на одному інстансі. Для продакшену — Postgres-реалізація (Prisma або Drizzle) за тим самим інтерфейсом, ніяких змін у викликах. Дані клієнтів: згода на обробку збирається, телефони/пошта не потрапляють у звіт `/report` та в аналітику.

## 8. AI (плановане, не в MVP-коді)

Дозволено: видобуток параметрів із рахунків/документів (OCR → структуровані поля, **з підтвердженням користувача**), нормалізація описів сировини до каталогу, виявлення пропусків, пояснення сценаріїв, чернетка звіту. **Заборонено:** вигадувати виходи метану чи ціни обладнання (джерело — тільки каталог, лабораторія, комерційні пропозиції), видавати скринінг за детальний інжиніринг, приймати рішення з безпеки. Технічно: LLM отримує лише `Assessment` як контекст і не має доступу до змінення параметрів.

## 9. Безпека та експлуатація

- Валідація всіх входів, обмеження розмірів; honeypot + ліміт 8 запитів/год/IP (в пам'яті — для масштабування Redis/WAF).
- CRM закрито без секретів у production (fail-closed).
- Відсутні зовнішні мережеві залежності під час виконання (шрифти — системні), немає трекерів; подієвий шар `dataLayer` для GA4/GTM підключається змінною.
- Безпека біогазових об'єктів: дисклеймер у кожному звіті; усі інженерні проєкти — тільки після перегляду фахівцями.

## 10. Тестування та якість

`npm test` (Vitest, 38 тестів): конверсія голів, реалістичність виходу метану, лінійність, збереження енергії, «тепло ≤ попиту», клімат, порядок сценаріїв, відсутність субсидій, NPV/IRR, чутливість, незалежність країни, провенанс усіх параметрів, відсутність HIGH-довіри без лабораторії, відсутність NaN, вердикти. `npm run typecheck`, ESLint, `next build`. Скрипти: `scripts/explore.ts` (таблиця кейсів), `scripts/sweep.ts` (розгортка масштабів), `scripts/calib.ts` (CAPEX проти опорної точки), `scripts/generate-registry.ts`.

## 11. Дорожня карта архітектури

1. **Фаза 1 (MVP, зроблено):** калькулятор, звіт, ліди, методологія.
2. **Фаза 2:** Postgres, збереження сценаріїв, PDF-звіт на сервері, завантаження ERA5/Open-Meteo, GIS (Leaflet + OSM, радіус сировини, відстані до газу/мережі, охоронні зони), кластерний режим (кілька ферм → один завод), інтеграція прайсів (рахунки).
3. **Фаза 3 (лише після валідації моделі):** Biogas Intelligence & Operating Platform — датчики, прогноз виробництва, аналітика виходу метану, моніторинг КГУ, предиктивне обслуговування, оптимізація. Свідомо **не** будується в MVP.
