# Поточний стан і пріоритети

Перевірено за робочим деревом 2026-10-28. Це стан реалізації, а не сертифікація
точності, свіжості всіх зовнішніх даних або готовності production-середовища.
Оновлюйте цей файл при зміні статусу; не додавайте щоденні звіти.

## Що вже працює

- Methalytics: безкоштовний screening → два автоматичні платні звіти для одного
  проєктного вводу. Експертна послуга не продається.
- Детермінована модель від сировини до трьох енергетичних маршрутів, сценаріїв,
  CAPEX/OPEX, pre-tax NPV/IRR, окупності й спрощеного DSCR.
- Країнові параметри, provenance, перевірка давності даних, пошук міста
  GeoNames із підготовленим кліматом ERA5; оплата Stripe і знімки результатів.
- На дату огляду: 33 країни, 25 UI-локалей; ці кількості не є гарантією
  однакової повноти моделей, перекладів або регіональних ринкових доказів.
  Актуальні каталоги: `src/countries/index.ts`, `src/i18n/config.ts`.

## Відкриті питання та умови закриття

| Пріоритет / питання | Підстава | Наступний результат і критерій приймання |
|---|---|---|
| P1. Класифікація й покриття бізнес-моделей | Власник не прийняв 29 категорій / 4 групи як остаточне рішення. У `src/core/businesses.ts` шість `outside_model`; частина інших напрямків має лише screening-наближення | Дослідити бізнеси, розділити галузь / роль / процес / масштаб; перевірити назви з місцевими фахівцями. Для кожного запропонованого розрахункового напряму — відповідні входи, процесна модель, економіка, джерела та незалежні контрольні кейси. Зняття блокування або заміна напису не є реалізацією моделі |
| P1. Обіцянка «без субсидій» і legacy input | `src/server/validate.ts` приймає `assumedSupportEurPerKwh`; `economics.ts` додає його до базової виручки, `assess.ts` лише позначає supportIncluded | Узгодити поведінку з продуктовою обіцянкою: перевірити потребу сумісності, відокремити підтримку або явно звузити обіцянку; додати регресію на дозволений input. У цьому docs-аудиті формулу/API не змінено |
| P1. Зовнішня валідація точності | Автотести перевіряють узгодженість; незалежна перевірка за фактичними заводами не підтверджена | Відокремити calibration від hold-out кейсів за маршрутом, масштабом, країною; зіставити виміряний CH₄, CAPEX/OPEX і відхилення. Узгодити допустиму похибку до підгонки. Див. `quality.md`, `capex-benchmark.md` |
| P1. Актуальність і застосовність локальних цін | Є historical FX, estimates, часткові відмови завантаження та непідтверджений offtake | `audit-model.ts` на дату оцінки → оновити суттєві параметри за періодом, тарифним класом і географією → перевірити вплив на NPV. Прогалини й pipeline: `data-sources.md`; LOW не прибирати без доказу |
| P1 перед продажами. Надійність оплати й зберігання | Локальні JSON, процесна черга запису, приватні bearer-посилання; deployed setup тут не перевірений | Перевірити persistent storage/restore, реальні Stripe test-mode webhook/poll/refund flows, захист URL/PII, відновлення доступу, юридичні реквізити. Для кількох writer-процесів потрібне спільне транзакційне сховище. Деталі: `payments.md`, `quality.md` |
| P1 перед обіцянкою повної локалізації. Інженерні тексти | `CoreLang` лише EN/UK; решта UI-локалей можуть бачити англійські пояснення | Перекласти структуровані причини, попередження й рекомендації, перевірити їх у повних звітах носіями-фахівцями. Наявність ключів не доводить природність мови. Див. `i18n.md` |
| P2. Фінансова повнота | `finance.ts`: EBITDA-based project flows, без податків, depreciation, working capital, construction financing; DSCR = EBITDA / ануїтет | Визначити потрібний рівень feasibility; реалізувати й звірити project/equity cash flow та lender CFADS до заяв про bankability. Поточний screening не називати after-tax моделлю |
| P2. Комерційні гіпотези | Ціни, попит і перевага Extended не підтверджені експериментом; `analytics.ts` лише пише в dataLayer | Перевірити доставку подій у систему аналітики, визначити метрики й кваліфікацію лідів, провести інтерв'ю/експеримент. Реєстр гіпотез: `market-research.md` |

P1 означає пріоритет роботи або умову конкретної обіцянки/релізу, а не заборону
незалежних косметичних чи дослідницьких задач. Порядок між P1 визначає поточна
ціль користувача. Розширення розрахункових моделей у межах цього аудиту
документації не виконувалося.

## Як не перетворити цей файл на журнал

Для кожного відкритого питання зберігайте підставу, наступну дію та доказ закриття.
Після виконання перенесіть сталий висновок у тематичний документ і приберіть
закритий рядок. Команди перевірок — у `quality.md`; поточні результати запусків
повідомляйте в підсумку задачі, не накопичуйте логи й лічильники тестів тут.
