# Якість, валідація та готовність до запуску

Джерела перевірок: тести поруч із кодом; `package.json`; `scripts/audit-model.ts`.
Цей документ замінює датований engineering-аудит: зберігає сталі критерії й межі,
а не історичні лічильники PASS. Відкриті пріоритети — [current.md](current.md).

## Рівні доказу

1. **Code correctness:** формули, одиниці, інваріанти, edge cases та регресії.
2. **Engineering validity:** незалежні виміри/реалізовані об'єкти, відповідна
   технологія й зіставні межі поставки. Дані калібрування не є hold-out перевіркою.
3. **Site feasibility:** лабораторія, договори на сировину/збут, EPC-оферти,
   приєднання, дозволи, фінансування й місцеві податки конкретного майданчика.

Успішний build доводить можливість зібрати застосунок. Тести синтетичних проєктів
доводять лише те, що перевіряють їхні assertions. Жоден із цих фактів сам по собі
не доводить точність CAPEX, доступність стимулів або доцільність будівництва.

## Verification за типом зміни

| Зміна | Необхідна перевірка |
|---|---|
| Формула / одиниці / параметри / країна | Незалежний контрольний розрахунок; тести `src/core/__tests__`; баланси по маршрутах/сценаріях; порівняння результату до/після; перевірка source date, applicability і sensitivity |
| Feedstock / бізнес-категорія | `businesses.test.ts`, `core.test.ts`, API validation; відповідний процес, а не лише нова назва; сумісність старих ID, чернеток, прикладів та оплачених snapshots |
| Оплата / доступ / persistence | `src/server/__tests__/payments.test.ts`; підпис і binding quote, сума/валюта, повторні й запізнілі події, snapshot, відсутній/неправильний token; Stripe test-mode end-to-end перед релізом платіжних змін |
| UI / локалізація / shared preferences | `src/i18n/__tests__`, `src/lib/__tests__`; SSR/hydration, клавіатура, mobile, довгі переклади; країна/мова/валюта/чернетка не змінюють значення непомітно |
| Пошук міста / клімат | `src/server/__tests__/cities.test.ts`; country binding і HMAC, dataset manifest/checksums, provenance, збережена локація, відсутність runtime API-залежності |
| Документація | Звірити твердження з кодом; перевірити шляхи/посилання/команди, відсутність дублікатів і суперечностей. Не створювати тести, що перевіряють лише власний текст |

Стандартні перевірки коду: `npm test`, `npm run lint`, `npm run typecheck`,
`npm run build` (PowerShell: `npm.cmd`). Не запускайте typecheck одночасно з
build, що змінює `.next/types`; не перебудовуйте активний dev/build-каталог
іншої сесії. Після релевантних тестів не повторюйте весь набір без нової причини.
Непройдену чи незапущену перевірку явно зазначайте; не називайте її PASS.
На дату цього огляду checked-in `.github` CI workflow немає; перелік команд
не означає, що вони автоматично запускаються при кожному PR.

Корисні діагностики без запису: `npx tsx scripts/audit-model.ts --as-of YYYY-MM-DD`,
`npx tsx scripts/calibrate-capex.ts`, `npx tsx scripts/benchmark.ts`,
`npx tsx scripts/sweep.ts`, `npx tsx scripts/thresholds.ts`.
Дату підставляйте свідомо; сьогоднішня дата не робить старі дані свіжими.
Завантажувачі та їхні режими запису — у [data-sources.md](data-sources.md).

## Баланси та критичні інваріанти

- **Mass:** fresh mass → TS/DM → VS; т/рік, кг/добу, відсоток і частка не
  взаємозамінні. `digestate + dry gas ≈ input` — поточне наближення, не повний
  водний/елементний баланс. Перевіряти також нульові, сезонні й крайові потоки.
- **Methane:** потенціал BMP → реалізація процесу → витоки → CHP/котел/upgrading/
  факел. Проскок upgrading застосовується лише до відповідного потоку; не
  множити втрати двічі. Біогаз, чистий CH₄ і товарний біометан — різні об'єми.
- **Energy:** Nm³ × LHV → kWh; потужність kW ≠ річна енергія. Місячні генерація,
  own loads, імпорт/експорт, процесне й корисне тепло мають зводитись із річними.
  Відсутній споживач тепла не створює дохід; літній надлишок не покриває зимовий
  дефіцит. HRT і OLR перевіряти одночасно, обладнання — за піком і availability.
- **Finance:** сума CAPEX/OPEX/revenue lines → EBITDA → cash flows → NPV.
  Перевіряти IRR без кореня/з кількома змінами знаку, нульовий борг, від'ємний
  EBITDA та відсутню окупність. Не змішувати project й equity метрики.
- **No double counting:** gate fee і уникнена утилізація; закупівля й втрачений
  продаж тієї самої сировини; тепло й газ, що його виробив; поживні речовини
  власного гною; субсидія в базі й у support case. Від'ємна ціна сировини —
  дохід від приймання, а не помилка знака за замовчуванням.
  Окремо перевірити legacy `assumedSupportEurPerKwh`: зараз воно може потрапити
  в base, попри загальну продуктову обіцянку (див. current/economics).
- **Evidence:** `USER_INPUT` не дорівнює перевіреному виміру. Високий confidence,
  нова дата огляду, кліматична локація чи назва галузі не підтверджують місцевий
  тариф, технічну придатність або ймовірність купівлі.

## Межі поточної інженерної моделі

| Частина | Чого ще не доводить розрахунок |
|---|---|
| Сировина / pretreatment | Сезонні лабораторні характеристики, фактичні домішки й втрати органіки; OPEX відсіву не означає повного mass balance відсіву |
| AD / технологія | Кінетика, COD-based дизайн UASB/EGSB, TAN/FAN/VFA, біологічна стійкість. Вибір технологічної назви не означає повноцінної окремої моделі |
| Газ / upgrading | H₂S, H₂O, N₂/O₂, силоксани, dew point, гарантії якості для конкретної мережі/двигуна, part-load, тиск і резервування N+1 |
| Енергія / availability | Погодинний dispatch, буфер газу, фактичні ремонти, гарантований покупець тепла, параметри конкретного CHP/компресора |
| Дигестат | Повний водний/N/P/K баланс, NH₃/N₂O, post-treatment/компостування, патогени, права на внесення та продуктовий статус у конкретній юрисдикції |
| CAPEX / логістика | Технічні умови приєднання, геологія, дорожні маршрути, фактичний EPC scope й актуальна комерційна ціна |
| Фінанси | Податки/ПДВ, depreciation, working capital, drawdown/IDC, reserve accounts, equity IRR та lender CFADS. Поточний DSCR — screening proxy |

Для переходу до site feasibility потрібні протоколи сировини, process design
basis, зіставні технічні пропозиції, угоди збуту/постачання, місцеві дозволи й
фінансова звірка. Модель можна й потрібно розширювати; ці межі описують код,
а не забороняють кращий метод. Наукові орієнтири попереднього аудиту:
[IEA BMP testing](https://task37.ieabioenergy.com/wp-content/uploads/sites/32/2022/02/Batch_tests_web_END.pdf),
[EPA AgSTAR handbook](https://www.epa.gov/agstar/agstar-project-development-handbook),
[IEA flexible bioenergy](https://task44.ieabioenergy.com/wp-content/uploads/sites/12/2021/08/IEA-Task-44-report-Technologies-for-Flexible-Bioenergy.pdf).
Це джерела методів, а не підтвердження сучасних цін; актуальність конкретної
норми/специфікації перевіряється в задачі, яка її використовує.

## Security та production

- Report token — bearer credential: знання URL дає доступ, зокрема до імені,
  компанії або email у заголовку звіту. `noindex` не є контролем доступу.
  Не передавати token/PII в аналітику, сторонні запити, приклади або логи.
- Перевіряти server-side input, country/region binding, підписи location/quote,
  строк quote, webhook signature і платіжну суму/валюту. Клієнт не встановлює ціну.
- JSON persistence і rate limits діють у межах процесу. Для production
  підтвердити один writer + persistent volume або впровадити спільне сховище;
  зробити restore rehearsal. Наявність atomic rename не забезпечує multi-instance ACID.
- Перевірити HTTPS, trusted geo headers, стабільність серверних secrets,
  закритий `/admin`, вимкнений demo payment, актуальні seller/terms/privacy.
  Не читати/публікувати значення `.env`, не виконувати реальних оплат під час QA.
- Webhook retry, polling, provider outage, refund і втрата посилання мають бути
  перевірені на deployed staging. Mock-тести не підтверджують зовнішню доставку.
- Локальні dataset assets мають потрапляти в build tracing; ліцензії GeoNames,
  ERA5, прапорів і шрифтів зберігаються. Перевірити встановлені залежності й
  застосовність security advisories перед релізом; автоматичний upgrade без
  перевірки сумісності не є виправленням.

## Підтримка знань

У підсумку суттєвої задачі вкажіть: що змінилося, чому, що перевірено та що
залишилося невизначеним. Зміна поведінки оновлює відповідний тематичний документ;
стале рішення — таблицю в `architecture.md`; доказ/статус гіпотези —
`market-research.md`; пріоритет — `current.md`. Не копіюйте таблиці параметрів,
повні результати тестів або цей checklist в нові файли.

## Незалежні референси та порівнянність

Held-out BV Dairy (Clearfleau, December 2014, slide 9; 200 m³/d, COD 25,400 mg/L, removal 98%, biogas 127 Nm³/h at 60% CH₄): за незмінених biomass/capture припущень модель дає 105.36 Nm³/h (−17.04%). Навіть повна COD-to-CH₄ стехіометрична межа з наведених входів — 120.54 Nm³/h, нижче оприлюднених 127. Параметри можуть належати різним проєктним/експлуатаційним умовам; не калібрувати модель, порушуючи COD balance. Джерело: https://conferences.aquaenviro.co.uk/proceedings/clearfleau-three-case-studies-converting-food-production-residues-into-energy/richard-gueterbock-2/ . Контроль — processes.test.ts.

TH cassava (2021): модель дає 40,796 Nm³/d проти оприлюднених 41,000 m³/d, але нормальні умови джерела та частка COD у біомасі/втрати газу не підтверджені. Близькість цих чисел не є доказом похибки <1%. HRT 15 d у статті суперечить V/Q=25.3 d; у сценарії застосовано V/Q, суперечність позначена.

Dagenham: каталожний food_waste на 160 kt/a дає 19.98 млн Nm³/a проти приблизно 14 млн m³/a з референсу JHA (https://www.j-h-a.co.uk/projects/refood-dagenham.html), різниця +42.71%. Capacity ≠ annual actual throughput, DM/BMP/contamination та газові умови джерела невідомі. Цей check виявляє недостатність універсального default; це не придатний calibration target чи доказ передбачуваної похибки моделі.

Не встановлено незалежної статистичної accuracy для всіх процесів/країн або перевіреної after-tax/project/equity фінмоделі за рахунками реальних заводів. До таких заяв потрібні зіставні operating datasets, EPC scope, періоди й відокремлений hold-out набір. Source observations у нових прикладах і невідомі бюджети перевіряються тестами та локалізованим SSR.
